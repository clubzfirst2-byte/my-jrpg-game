# 2Dオープンワールド・アクションアドベンチャー 設計書・実装計画（v0.3）

HTML / CSS / JavaScript で作るブラウザ向け2D見下ろし型オープンワールド・アクションアドベンチャー（iPhone対応）の設計書と開発計画です。
既存作品のキャラクター・名称・マップ・音楽・画像は一切使わず、完全オリジナルで制作します。

## 0. コンセプト

- 2D見下ろし型のオープンワールド。広いフィールドを継ぎ目なく探索できる
- 高品質なドット絵
- 一本道ではなく、攻略の順番も方法も自由
- スマートフォン（特に iPhone）で快適に遊べる
- HTML / CSS / JavaScript が基本。描画は WebGL（PixiJS v8）
- 最初から全機能を作らず、遊べる小さな試作品から段階的に作る。段階ごとに動作テストを行う

## 1. 技術構成

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | JavaScript（ES Modules）＋ JSDoc 型注釈（`// @ts-check`） | HTML/CSS/JS が基本という条件を守りつつ、型チェックで大規模化に備える |
| ビルド・開発サーバ | Vite | 速い。スマホから同じ LAN の PC につないで確認できる |
| 描画 | **PixiJS v8（描画専用）** | iPhone でも大量のスプライトやライティングを描きやすい。描画層の中だけで使う |
| 物理 | 自作の軽量物理（円 / AABB ＋高さ） | 見下ろし視点で「高さ」を扱うため、汎用の物理エンジンは合わない |
| 環境シミュレーション | 自作。イベント駆動＋アクティブセル方式（4章） | 変化した場所だけ計算する |
| 音 | Web Audio API | iOS のオーディオ制限（最初のタップで解禁）に対応 |
| セーブ | IndexedDB（使えない時は localStorage） | オートセーブとスロット管理 |
| 配布 | PWA ＋ GitHub Pages | iPhone 実機ですぐ試せる URL を常に用意する |
| テスト | Vitest（ロジック）＋ Playwright（E2E）＋ **iPhone 実機テスト（必須）** | 自動テストと実機確認の両方を通過条件にする |
| CI | GitHub Actions | push 時にテストを実行し、Pages へ自動デプロイ |

### 1.1 ゲームロジックと描画層の完全分離

```
┌──────────── src/game/（ロジック層）────────────┐
│ 入力アクション → 状態更新（固定60Hz）→ ゲーム状態 │   ← PixiJS・DOM・window を一切参照しない
└───────────────────────┬────────────────────────┘
                        │ 読み取り専用（毎フレーム）
┌──────────── src/view/（描画層）────────────────┐
│ 状態を読み、補間して PixiJS で描く               │   ← 状態を書き換えない
└────────────────────────────────────────────────┘
```

- ロジック層は**純粋な JavaScript**。Node 上でそのまま単体テストでき、画面なしでも動く
- 描画層はロジックの状態を**読むだけ**。描画の問題がゲームの挙動に影響しない
- 依存方向は ESLint の `no-restricted-imports` で強制する（`src/game` から `pixi.js` や `src/view` を import したらエラー）
- 入力も「タッチ・キーボード・パッド → 共通アクション（`move`, `attack`, `jump`…）」に変換してからロジックへ渡す

### 1.2 初期段階では複雑な ECS を作り込まない

- 最初は**素直なオブジェクト＋配列＋更新関数**で作る（例：`entities[]` と `updateMovement(entity, dt)`）
- データ駆動（JSON で敵やアイテムを定義）は最初から採用する。ECS の汎用的な仕組みは作らない
- 性能や構造の問題が**実測で**見えた時点で、必要な部分だけ整理する

### 1.3 フレームレート：60fps 目標、30fps でも快適

- **ロジックは固定 60Hz**（アキュムレータ方式）。描画は端末の表示周期で行い、前後の状態を補間する
- 描画が 30fps に落ちても、**ゲームの速度・判定・入力の結果は変わらない**
- タイミングは**フレーム数ではなくミリ秒**で定義する（例：ジャスト回避の受付 150ms、先行入力 120ms）。30fps でも最低 3〜4 フレーム分の猶予を確保する
- 端末が遅いときは**品質レベル**（高 / 中 / 低）を下げる：パーティクル数、ライティングの解像度、天候エフェクト、影
- 処理落ちが続く場合の上限：1 フレームで回すロジック更新は最大 4 回。それ以上は時間ごと捨てて、ワープしたような挙動を防ぐ

### 1.4 iPhone 実機での性能測定を優先（Mac がなくても確認できる）

**Mac の Safari Web Inspector がなくても、iPhone 単体で性能と不具合を確認できる**ことを前提にする。

| 仕組み | 内容 |
|---|---|
| ゲーム内の計測表示 | FPS、フレーム時間（平均・遅い方から 5%・最大）、描画呼び出し数（ドローコール）、表示オブジェクト数、テクスチャ数、内部解像度、端末情報。画面右上のボタンで表示の切り替え |
| ゲーム内のエラー表示 | 実行時エラー・Promise の失敗・`console.error` を画面上に赤く表示し、件数を記録する。ゲームを止めずに確認できる |
| 計測レポート | 「計測開始」で一定時間（初期値 30 秒）計測し、結果を Markdown で表示。「コピー」ボタンでコピーして `docs/device-tests/` に貼れる |
| URL パラメータ | `?debug=1` で計測表示を最初から開く。`?bench=N` で負荷テスト用のスプライト数を指定 |
| GitHub Actions | push とプルリクエストのたびに、Lint・型チェック・単体テスト・ビルド・E2E を実行。結果の要約を Actions の画面（Job Summary）に表示し、E2E のスクリーンショットとレポートを成果物として保存 |
| 実機テスト記録 | `docs/device-tests/` に、雛形（TEMPLATE.md）をコピーして段階ごとに記録する。計測レポートはそのまま貼り付けられる形式にする |

- 計測結果は `docs/perf/` にも段階ごとに要約し、前の段階より悪化していないか比べる
- Mac の Safari Web Inspector は、使える場合の補助として扱う（必須にしない）

### 1.5 描画は PixiJS v8 の WebGL に固定

- PixiJS v8 は `preference: 'webgl'` を明示して初期化する（WebGPU は使わない）
- 初期段階では複数の描画方式（WebGPU、Canvas 2D への自動切り替えなど）を管理しない。描画の不具合を調べる対象を一つに絞る
- WebGL の初期化に失敗した場合は、画面にエラー内容と対処（ブラウザの更新など）を表示する
- iPhone 実機では、性能（FPS・フレーム時間）と安定性（長時間プレイ、アプリ切り替え後の復帰、WebGL コンテキストの喪失と復帰）を段階ごとに確認する

## 2. iPhone 対応

### 2.1 内部解像度の比較検証（P1 で実施）

高さは固定し、横幅は画面比率に合わせて伸ばす（iPhone の横長画面で左右に黒帯を出さない）。

| 候補 | 表示タイル数（16px、16:9時） | 長所 | 懸念 |
|---|---|---|---|
| 320×180 | 20×11.25 | キャラが大きく見やすい。最も軽い | 視野が狭い。UI を置く余白が少ない |
| 384×216 | 24×13.5 | バランスが良い | 整数倍にすると端末によって余りが出る |
| 480×270 | 30×16.9 | 視野が広く、探索しやすい | キャラが小さい。負荷が高い |

- **実装方法（P1）**：候補の高さを「目標」とし、1 ドットを端末の画素で何倍にするか（整数倍）を、内部の高さが目標に最も近くなるように決める。そのうえで内部の幅と高さを画面全体を覆う大きさにする（黒帯なし、はみ出しは 1 ドット未満で上下左右に均等に切る）。そのため実際の内部の高さは端末により目標から少しずれる（例：iPhone 15 Pro 横向き・目標 216 → 内部 512×236、1 ドット = 5×5 画素）
- デバッグメニューで 3 案をその場で切り替えられるようにする
- 判定基準：①キャラと敵の見やすさ ②操作ボタンを置いても視野が十分か ③FPS ④ドットのにじみ（整数倍に拡大できるか）
- P1 の終わりに実機で比べて**1 案に決定**し、この設計書に記録する
- **決定（P1、2026-11-03）：216**。180 は近すぎ、270 は遠すぎた。探索目標の見通し・滑空・戦闘の視野を優先。キャラクターを大きく見せたい場面は、カメラの自動ズームとして P3 以降で検討する（docs/device-tests/2026-11-03-P1.md）

### 2.2 テクスチャの読み込み・解放の管理

- `AssetManager` を一か所に作り、素材は**論理名**で指定する（例：`player.walk`）。実際のファイルの場所は素材マニフェストで管理する（7.5 節）
- 素材は**束（バンドル）**単位で読み込む：「共通（UI・プレイヤー）」「地方ごと」「ダンジョンごと」
- 参照カウントを持たせ、使わなくなった束は解放する（`Assets.unload` と `texture.destroy`）
- テクスチャメモリの予算を決め（目安 128MB 以下）、デバッグ表示で常に確認する
- アトラスは 1 枚 2048px を基本とする（最大 4096px）

### 2.3 バックグラウンド移行時の一時停止と復帰

| きっかけ | 処理 |
|---|---|
| `visibilitychange`（hidden）、`pagehide` | ゲームループを停止、AudioContext を一時停止、**オートセーブ** |
| 復帰（visible） | 経過時間をリセット（復帰した瞬間に大量の更新を回さない）、一時停止メニューを表示し、タップで再開（音声の再解禁も兼ねる） |
| `webglcontextlost` / `restored` | 描画を止め、復帰したらテクスチャを読み込み直す。ゲーム状態はロジック層にあるので失われない |
| 画面回転・サイズ変更 | 内部解像度と拡大率を再計算し、UI を再配置する |

### 2.4 長時間プレイの測定

- 測定のタイミング：P3.5（最初の島）以降、各段階の終わり
- 測定内容：30 分と 60 分の連続プレイで、①FPS の推移（発熱による性能低下が出ていないか）②メモリが増え続けていないか ③電池残量の減り方 ④本体の発熱（手で触った感覚の 3 段階）
- 記録用の表を `docs/perf/` に用意し、毎回同じ手順で測る

### 2.5 テスト方針（実機テストは必須）

| 種類 | 内容 | 通過条件 |
|---|---|---|
| 単体テスト | ロジック層（当たり判定、移動、ダメージ、環境ルール） | 全件成功 |
| E2E（Playwright） | iPhone サイズの画面で起動・操作・スクリーンショット | 全件成功、表示崩れなし |
| **iPhone 実機** | 段階ごとのチェックリスト（7.3 節）で操作性と性能を確認 | チェックリストをすべて満たす |

画面の調整：`100dvh` と safe-area-inset でノッチやホームバーを避ける。ピンチズーム、スクロール、長押しメニューは無効化。横画面を推奨し、縦画面では回転を促す表示を出す。

### 2.6 セーブデータ（実装は P3.5 の簡易セーブから）

**保存先**

| データ | 保存先 |
|---|---|
| ゲームの進行（位置、所持品、フラグ、環境の差分など） | **IndexedDB**（基本） |
| 設定（音量、ボタン配置、解像度、計測表示の有無など小さなデータ） | localStorage（数 KB 以内に限定） |

**バージョン管理**
- すべてのセーブに `schemaVersion`（形式の版）と `gameVersion`（ゲームの版）を付ける
- 形式を変えるときは、移行関数（`v1 → v2 → v3 …`）を順に適用して読み込む。移行関数ごとに単体テストを書く
- 自分より新しい形式のセーブは読み込まず、「ゲームを更新してください」と表示する（データは消さない）

**破損を防ぐ仕組み**
- スロットごとに**2 世代（A / B）を交互に書き込む**。書き込み中に中断されても、前の世代が残る
- 書き込みは 1 つの IndexedDB トランザクションで行い、データ本体と「どちらが最新か」の情報を同時に確定させる（途中で止まれば両方とも反映されない）
- データにはチェックサムを付け、読み込み時に検証する。壊れていれば前の世代から読み込み、ユーザーに知らせる
- 保存のきっかけ：オートセーブ（一定時間ごと・エリア移動時）、手動セーブ、アプリ切り替え時（`visibilitychange` / `pagehide`）。アプリ切り替え時の保存は時間が足りずに失敗することがあるため、それだけに頼らずオートセーブを併用する
- 保存処理が重なったら、後の要求を 1 つにまとめて順番に実行する（同時に書き込まない）
- iOS の容量削除への備えとして、`navigator.storage.persist()` を要求する

**保存失敗時の通知**
- 失敗したら画面にはっきり通知する（「保存できませんでした。空き容量を確認してください」など）。原因（容量不足・プライベートブラウズ・その他）ごとに文言を分ける
- 失敗しても前の世代のデータは残っているので、そのまま遊び続けられる。次の保存で再試行する
- 書き出し機能（セーブを文字列でコピーする）を用意し、万一に備える（P3.5 以降）

## 3. 高さの表現

### 3.1 座標の分離

| 値 | 意味 |
|---|---|
| `x, y`（足元座標） | 地面上の位置（マップ座標）。当たり判定と移動はこの座標で行う |
| `terrainHeight(x, y)`（地形標高） | その地点の地面の高さ。タイルのデータから求める（1 段 = 16px。P2 で 8px から変更） |
| `z`（キャラクターの高さ） | キャラクターの絶対的な高さ。`z > terrainHeight` なら空中にいる |
| `screenX = x - camX`, `screenY = y - z - camY`（描画座標） | 描画層だけが計算する。ロジック層は持たない |

- 影は `(x, y - terrainHeight)` に描く。空中ではキャラクターと影が離れ、高さが分かる
- 高い場所のタイルも同じ規則で、その標高の分だけ上にずらして描く

### 3.2 地形の種類

| 種類 | 定義 | 移動 |
|---|---|---|
| 段差 | 高さの差 8px（半段）以下 | 歩くだけで自動的に上り下りできる |
| 斜面 | 高さが連続的に変わるタイル（方向付き） | 歩ける。急な斜面は登りが遅く、ダッシュでスタミナを使う |
| 崖 | 高さの差 1 段以上 | 歩いては越えられない。ジャンプで届けば上れる。飛び降りは可能で、高すぎると落下ダメージ |
| 登攀可能な壁 | 崖のうち、素材が「岩・土・蔓」 | 登攀できる（P2.1） |
| 登攀不可の壁 | 崖のうち、素材が「磨かれた遺跡の壁・氷」 | 登れない。別のルートや能力を使う |

タイルのデータ：`{ elevation, shape: flat | slope(向き), material }`。崖かどうかは隣のタイルとの高さの差から自動で判定し、手作業の設定を減らす。

### 3.3 描画順

```
1. 地面（標高の低い層から順に）
2. 崖の側面
3. 影
4. Y ソートの層：キャラクター・木の幹・岩・建物の壁
   並び順 = 足元の y（マップ座標）。同じなら z が大きい方を後に描く
5. 覆いかぶさる層：木の葉、屋根、アーチ
   プレイヤーが後ろに隠れたら半透明にする
6. エフェクト → 7. 天候 → 8. ライティング（昼夜・光源） → 9. UI（DOM）
```

- 大きな物体（建物など）は足元の線で並べるため、**足元の基準点（アンカー）**を素材ごとにデータで持つ
- 遮蔽物の後ろにいるプレイヤーは、シルエット表示も選べるようにする

### 3.3.1 実装メモ（P2）

- 並び順のキー：キャラクターと物体は「足元の y」、高くなっている地形は「その行の北端の y」。この 1 つの規則で、崖の北（後ろ）にいれば隠れ、崖の上に立てば崖より手前、崖の南にいれば手前に描かれる
- 高さの読みやすさ（実機の感想「一目では分かりにくい」を受けて強化）：1 段の崖をタイル 1 枚分（16px）の高さで描く、高い地面ほど明るく描く（1 段ごとに明るさ +7%）、崖の下と右側の低い地面に影を落とす（光は左上から）、高い場所の縁を 2 ドットの線で囲む
- 坂は「北に向かって 1 段上がる」形だけを扱う（見下ろし視点で正面に見える階段）。東西向きの坂は必要になった時点で追加する
- 地形の高さはタイル単位の高さ地図で表すため、**橋（上も下も通れる場所）は表現できない**。橋は「高さを持つ物体（足場）」として、物理オブジェクトと合わせて後の段階で実装する（9 章）
- 物理の数値（P2）：1 段 = 16px、歩いて上り下りできる段差 = 8px（半段）、ジャンプの高さ = 20px（1 段には届き、2 段には届かない）、重力 900px/s²（滞空時間は約 0.42 秒）、安全に落ちられる高さ = 3 段（48px）。それを超えると 1 段ごとにハート半分のダメージ
- 操作の猶予：崖から落ちた直後 0.08 秒はジャンプできる（コヨーテタイム）。着地 0.12 秒前に押したジャンプは着地と同時に出る（先行入力）
- 体力が 0 になったときは、P3（死亡処理）までの仮の処理として、開始地点に体力満タンで戻る

### 3.5 カメラ（P2 の後に先行実装）

| 項目 | 仕様 |
|---|---|
| 視点 | **斜め見下ろしの 3/4 視点**（オブリーク投影）。地面は真上から、崖・壁・木・キャラクターは南側（手前）の面が見える。画面上の位置 = (x, 足元の y − 高さ z)。真上視点やアイソメトリック（菱形）にはしない |
| 追従 | 主人公を画面中央に置き、**指数関数的な補間**で滑らかに追う（約 0.12 秒で距離の 63% を詰める）。フレームレートに依存しない（30fps でも 60fps でも同じ動き） |
| 追従の基準 | 通常は主人公の「足元の地面の高さ」を基準にする（ジャンプで画面が上下に揺れない）。滑空中・登攀中のように長く空中にいるときは主人公の実際の高さを基準にして、画面の中央付近に保つ（P2.2 で追加） |
| 瞬間移動 | 画面 1.5 枚分より離れたら補間せずに切り替える（復活・エリア移動）。`snapCamera()` で明示的にも切り替えられる |
| 範囲制限 | 表示範囲（境界）の外は映さない。境界より画面が広い場合は中央に寄せる。境界は差し替え可能で、**屋外はマップ全体、屋内・洞窟・ダンジョンは部屋や階の範囲**を設定する |
| ズーム | 倍率を変数で持ち、後から変更できる（1〜4 倍）。ドットを均等に保つため整数倍を推奨。確認用に `?zoom=2` |
| 解像度 | 内部解像度は目標の高さ 216（2.1）。横幅は端末の縦横比に合わせて伸ばし、整数倍で拡大 |
| ドットの鮮明さ | テクスチャは最近傍補間、キャンバスは `image-rendering: pixelated`、アンチエイリアスなし、カメラの位置は画面の 1 ピクセル単位にそろえる |
| 前後関係 | 3.3 の規則（キャラクター・物体は足元の y、高い地形の行は北端の y）。木や建物は足元を基準点にして並べる |
| 画面の向き | 横画面が基本。縦向きのタッチ端末では「横向きにしてください」と表示する（閉じればそのまま遊べ、カメラも縦長に対応する） |

実装：`src/view/camera.js`（PixiJS に依存しない純粋なクラスで、単体テストあり）。

### 3.3.2 実装メモ（P2.1 登攀）

- **操作**：壁に向かって 0.2 秒押し続けると張りつく（空中では触れた瞬間）。壁に向かって倒す＝登る、反対＝下りる、横＝壁に沿って移動。どの向きの壁でも同じ
- **登り切り**：壁の上端に着くと自動で上に乗る。下りきって地面に着くと自動で離れる
- **手を離す**：登攀中にジャンプボタン。離した直後 0.4 秒は再びつかまない（落ちながらすぐ張りつくのを防ぐ）
- **登れない壁**：遺跡の壁、階段（坂）の側面、木・岩・水。半段（8px）以下の段差は歩いて上る（登攀にならない）
- **速さ**：上下も横も 24px/秒（1.5 タイル/秒）
- **スタミナ**（最大 100）：登攀で移動中 12/秒、張りついて止まっている間は消費なし。ダッシュ 20/秒。地面で 0.5 秒休むと 35/秒で回復。0 になると手が離れて落ち、満タンに戻るまで「疲労」状態（ダッシュ・登攀不可、歩く速さ 60%）
- **表示**：スタミナの輪をプレイヤーの横に表示（満タンのときは隠す。少ないと黄、疲労中は赤で点滅）
- **既知の見た目の制約**：3/4 視点では崖の東西の側面は描かれないため、東西の壁を登る姿は「崖の横に浮いている」ように見える（影で高さは分かる）。登攀専用の絵（壁に手をかける姿）は本番素材の段階で用意する
- 雨で滑る（5.3）は P5（天候）で追加する

### 3.3.3 実装メモ（P2.2 滑空）

- **開く**：空中で、地面から 12px 以上の高さがあるときにジャンプボタン（ジャンプの頂点付近で 2 回目を押してもよい）。低すぎるときの押下は先行入力として扱い、着地と同時にジャンプになる
- **閉じる**：もう一度ジャンプボタン。スタミナが 0 になったときも閉じる
- **飛行**：一定の速さ 22px/秒で降下、水平の速さ 80px/秒、操作に慣性あり（加速 300px/s²）。スティックを離すとその場で漂いながら降下する。4 段（64px）の塔からは約 230px（約 14 タイル）飛べる
- **スタミナ**：6/秒
- **着地**：滑空したまま着地すればダメージなし。途中で閉じた場合は、閉じた高さから落下ダメージを測る
- **崖にぶつかる**：登れる崖ならそのままつかまる（登攀へ）
- **表示**：プレイヤーの頭上に布の翼（仮素材）。カメラは滑空中・登攀中は実際の高さに追従する
- **入力の改善**：1 フレームより短いジャンプの押下（素早いタップ）も取りこぼさないようにした
- **未対応**：水はまだ「壁」扱いのため、池の上は飛べない（P2.3 水泳で水の扱いを変える）。上昇気流・風は P5 以降

### 3.3.4 実装メモ（P2.3 水泳）

- **水は「壁」ではなくなった**：水のタイルの高さが水面。自分と同じ高さ（段差 8px 以内）の水面に歩いて入ると泳ぎになる。高い崖の上から足先が水の上に出ただけでは泳がない（崖から落ちて水に入る）
- **泳ぎ**：40px/秒（歩きの約半分）、ダッシュで 64px/秒。ジャンプ・滑空はできない
- **スタミナ**：止まって浮いている間 3/秒、泳いでいる間 6/秒、ダッシュ中 18/秒。地面に上がるまで回復しない
- **溺れる**：スタミナ 0 で、最後に立っていた陸地へ戻り、ハート半分を失う（体力 0 になったら通常の復活）
- **岸**：同じ高さの岸へは泳いで上がれる。崖の岸は、登れる崖ならつかまって登れる（遺跡の壁などは不可）
- **落下・滑空**：高い所から水に落ちても落下ダメージなし。滑空中に水面に下りると翼を閉じて泳ぐ。水の上を滑空できるようになった
- **表示**：水面から頭と肩だけを出し、波紋を 2 コマで動かす（仮素材）。水面では足元の影を出さない
- **未対応**：深さ（浅瀬・深み）の区別、流れのある水、潜水は扱わない（必要になった段階で追加）

### 3.4 先に小さな検証マップを作る

P2 の最初に**高さ検証マップ**（およそ 40×30 タイル）を作る。段差、斜面、1〜3 段の崖、登攀可能と不可の壁、浮島、橋の下をくぐる場所、木と建物の遮蔽を 1 枚にすべて並べる。以降、高さに関わる変更をしたら必ずこのマップで回帰確認する。

## 4. 環境シミュレーション

### 4.1 基本方針

- **全タイルを常時計算しない**
- **イベント駆動＋アクティブセル方式**：何かが起きた場所（火矢が当たる、雨が降り始める、電気が流れる）だけを「アクティブ」にして計算する
- **変化したセルだけ保存**：地形の初期状態からの差分だけを疎なマップ（`Map<セル番号, 状態>`）に持つ

### 4.2 処理の流れ

```
イベント（着火・放水・放電）
   ↓
対象セルをアクティブ集合に追加
   ↓
10Hz ごとに、アクティブ集合のセルとその隣だけを計算
   ↓
変化があったセル → 差分の記録を更新、描画層に通知
状態が落ち着いたセル（燃え尽きた・乾いた）→ アクティブ集合から外す
```

- 1 回の計算で処理するセル数に**上限**を設ける（例：512 個）。超えた分は次回に回し、処理落ちを防ぐ
- プレイヤーから遠いアクティブセルは計算を止め、**止めた時刻と状態を記録**する。単純に燃え尽きさせることはしない（4.4）
- 灰から草が再生するのは時間の経過で判断する（「何時に再生する」という時刻だけ記録し、毎回は計算しない）
- 導電は毎回ではなく、**放電イベントのときに 1 回だけ**つながっている範囲を探索して求める（金属・水の連結範囲）

### 4.3 最初に作る範囲（P4）

| ルール | 内容 |
|---|---|
| 延焼 | 草・木が燃える。隣のセルに確率で燃え移る（燃料が尽きると灰になる） |
| 消火 | 水・雨で炎が消え、セルが濡れる（濡れたセルはしばらく燃えない） |
| 導電 | 金属・水の連結範囲に電気が流れ、範囲内の敵とプレイヤーにダメージ |

風による延焼方向の偏り、上昇気流、氷、温度は、基本の 3 つが安定してから追加する。

### 4.4 遠距離の変化を経過時間で再現する

遠くで起きた火事を「すぐ燃え尽きた」ことにすると、戻ったときに不自然になる（広がるはずの火が広がっていない、雨が降ったのに燃え尽きている、など）。そこで、**経過時間を考慮した簡易シミュレーション**を行う。

```
プレイヤーが離れる
   ↓
その地域のアクティブセルを「凍結」：状態と凍結した時刻を記録
   ↓（プレイヤーがいない間は何も計算しない）
プレイヤーが近づく（地域に入る少し手前）
   ↓
経過時間 = 現在時刻 − 凍結した時刻
   ↓
粗い時間刻み（例：1 秒）で簡易ルールを早送り
   ・延焼：燃料の量から燃える時間を求め、燃え移りは同じ規則で粗く計算
   ・その間の天候を考慮（雨が降っていたら、その時点で消火・濡れ）
   ・燃え尽きたセルは灰に。再生時刻を過ぎていれば草に戻す
   ↓
結果を確定し、通常の 10Hz 計算に戻す
```

- 早送りの計算量には上限を設け（例：1 フレームあたり最大 2ms）、数フレームに分けて行う。地域に入る**手前**から始めて、プレイヤーが着く頃に終わらせる
- 早送りは**シード付きの乱数**で行い、同じ条件なら同じ結果になるようにする（単体テストで確認できる）
- 経過時間がとても長い場合（例：ゲーム内で 1 日以上）は、最終状態を直接求める（燃える物は灰、時間が経っていれば再生）
- 戻ったときに燃え広がった跡（灰の範囲、焦げた木）が残っていて、「自分がいない間に燃え広がった」と分かる見た目にする
- 地域の外へ延焼が広がる場合は、隣の地域も凍結状態の一部として扱う（地域の境目で火が不自然に止まらない）

### 4.5 実装メモ（P4 環境シミュの基本）

- **場所**：`src/game/env/envSim.js`（規則・凍結・早送り）と `envActions.js`（火矢・剣・結晶・水がめ・ダメージ）。どちらも描画に依存しない
- **セル = タイル**。材質は地形と物から決まる：草・木・いばら（燃える）、水・金属の床（電気を通す）、砂・道・遺跡・岩（燃えない）
- **延焼**：10Hz で燃えているセルだけを計算。1 回の計算は**最大 512 セル**、超えた分は次回へ回す（順番に回すので、どのセルも止まり続けない）。隣の燃えるセルに毎回 10% で燃え移る。燃焼時間は草 3 秒・いばら 2 秒・木 12 秒。燃え尽きると灰になり、2 分後に草に戻る（時刻だけ記録し、毎回は計算しない）。木は切り株になって通れるようになり、いばらは消える
- **消火**：水がめを剣か矢で割ると、周り（距離 2）の火が消え、20 秒間濡れて燃えない。雨（P5）も同じ処理を使う
- **導電**：雷の結晶を剣か矢で叩くと、つながった水・金属のセルに電気が流れる（近い順に最大 400 セル・24 マスで減衰）。その上にいる敵は 8 ダメージで気絶、泳いでいる・金属の床に立っているプレイヤーは 1 ハート。受信柱が電気に触れると、つながった扉が開く（開いた扉はセーブされる）
- **火矢**：矢が燃えているセル・かがり火・たき火の上を通ると火矢になる。当たった所や落ちた所に火がつく。敵に当たると追加ダメージ
- **火と電気のダメージ**はガードできない。火は半ハートずつ（被弾後の無敵時間で間隔が空く）
- **凍結と早送り（4.4）**：島を 16×16 タイルの地域に分け、プレイヤーの地域とその周り 1 つ（3×3）だけを計算する（画面の外側に必ず 16 タイル以上の余白がある）。離れた地域は時刻を記録して止める。戻ると、1 秒刻みで経過時間ぶん早送りする。1 ステップの計算量に上限（3000 セル分）を設け、数フレームに分けて行う。10 分以上離れていた場合は、最後の 10 分だけを計算する（火は必ず燃え尽きている）
- **同じ結果になる仕組み**：乱数は「シード・セル番号・時刻」から作るハッシュなので、処理の順番やフレームの分け方に左右されない。早送り中の地域と外の境目をまたぐ延焼は、早送りが終わるまで保留して最後にまとめて反映する（単体テストで、分け方を変えても早送りの結果が同じことを確認）
- **島の仕掛け**：
  - 森の隠れ場所の入口をいばらでふさいだ。開け方は 3 通り：①かがり火越しに矢を撃つ ②森に火をつけて燃やす ③剣で 3 回切る
  - 野営地のたき火の周りを金属の床にし、西の端に結晶を置いた。結晶を叩くと、床の上の敵がしびれる（野営地の 4 つ目の攻略法）
  - 南東の浜に、扉で閉じた宝箱を置いた。受信柱は浜辺に、結晶は小島にある。小島の結晶を叩くと、海を通って電気が受信柱に届き、扉が開く
- **保存**：P4 では環境の状態（燃えた跡・灰）は保存しない。開いた扉だけ進み具合として保存する。差分の保存は P8（セーブの差分保存）で行う

### 4.6 実装メモ（P5 昼夜と天候）

- **場所**：`src/game/env/weather.js`（時刻・天候・明るさ。純粋な関数）、`weatherActions.js`（風・上昇気流・雨の壁・雷）、`src/view/weatherView.js`（ライト・雨・雷の描画）
- **時刻**：ゲーム内 1 時間 = 現実 1 分（1 日 24 分）。はじめからは 7:00。時刻はセーブされる
- **天候は「シードと時刻の関数」**：3 時間ごとに、晴れ 50%・くもり 25%・雨 17%・雷雨 8% で決まる。最初の朝（12:00 まで）は必ず晴れ。関数なので、遠くの地域の早送り（4.4）でも「その時刻に雨が降っていたか」が分かり、その時点で火が消える
- **雨**：外の燃えているタイルは 1 回の計算ごとに 8% で消える。雨の間と止んでから 20 秒は燃え移らない（火矢でも点かない）。洞窟の中は雨が届かない。崖を登ると、1.2 秒ごとに 10px 滑り落ちる
- **風**：天候ごとに向きと強さ（晴れ 0.2〜、雷雨 0.9〜）。火は風下へ最大 2.5 倍速く、風上へは遅く燃え広がる。くもり以上の日は、滑空中に風で流される（晴れの日は流されない）
- **上昇気流**：滑空中に燃えている所（周り 3×3）の上に入ると上昇する（地面から 112px まで）。草を燃やして高い所へ上がれる
- **雷雨**：1 秒に 12% の確率で、プレイヤーから 2〜10 マスの所に雷が落ちる。0.9 秒前に落ちる場所が点滅する。周り 20px にいると 1.5 ハート、水や金属に落ちるとつながった範囲に電気が流れる
- **明るさ**：時刻と天候から環境光を決め、ライトマップ（内部解像度の 1 枚のテクスチャ）を画面に乗算する。夜は、火・たき火・かがり火・結晶・プレイヤーの周りが光る。晴れた昼はライトマップを描かない（負荷 0）。手元の計測では、ライトマップの描画は 1 フレーム 0.1〜0.2ms
- **確認用の URL**：`?time=22`（時刻）、`?weather=rain`（天候を固定）、`?light=0`（ライトを消して負荷を比べる）
- **まだ無いもの**：雨で泳ぐ・料理などへの影響（P6 以降）、季節（P10）

### 5.3 アクション
移動 / ダッシュ（スタミナ消費）/ ジャンプ / 登攀 / 滑空 / 水泳 / 近接攻撃（3 段コンボ・溜め）/ 弓（狙う）/ 回避（ジャスト回避でスロー＋反撃）/ ガード（ジャストガードで弾き返す）

- **登攀**：崖の面に向かって進むと登り始め、スタミナを消費する。雨で濡れると滑る
- **滑空**：高い場所から飛び降りて滑空。のちに上昇気流と風の影響を追加
- **水泳**：スタミナを消費。尽きると溺れて岸に戻される

### 5.4 環境の元素ルール（最終的な全体像）

| 組み合わせ | 結果 | 実装時期 |
|---|---|---|
| 炎＋草木 | 延焼。燃えた跡は灰になり、時間が経つと再生する | P4 |
| 雨・水＋炎 | 消火。セルが濡れる | P4 |
| 電気＋金属・水 | 導電して範囲ダメージ。仕掛けの動力にもなる | P4 |
| 風 | 延焼方向・矢・滑空に影響 | P5 以降 |
| 炎の熱 | 上昇気流、氷が溶ける、寒さを防ぐ | P5 以降 |
| 冷気＋水 | 凍って足場になる | P7 以降 |
| 雷雨 | 金属装備に落雷 | P5 以降 |

### 5.5 時間・天候・四季
- 1 日＝実時間 24 分。光の色の変化と光源で昼夜を表現。夜は強い敵が出る
- 天候：晴れ・雨・雷雨・雪・砂嵐・霧。地方と季節ごとに起きやすさが変わる
- 四季：1 季節＝ゲーム内 7 日。見た目、採れる素材、出る敵が変わる（P10.2 で実装。8.4）

### 5.6 戦闘と成長
- **敵**：基本 4 系統（獣・澱の魔物・古代機械・亜人の野盗）×地方ごとの変種。中ボスが徘徊し、核ボスは 4 体＋ラスボス
- **敵 AI**：状態機械（見張る→気づく→攻撃→逃げる）
- **装備**：武器（剣・槍・大剣・弓・杖）は耐久度を持ち、鍛冶屋で強化・修理できる。防具は 3 部位
- **料理**：素材の組み合わせで回復＋一時効果。レシピは発見制
- **成長**：試練の報酬「星の欠片」で HP かスタミナを上げる。スキルツリーは「狩人／剣士／探求者」の 3 系統

### 5.6.1 実装メモ（P3 戦闘の基礎）

- **タイミングはすべてミリ秒**で定義（30fps でも同じ受付時間）。数値は `src/game/entities/playerCombat.js` と `enemies.js` に集約
- **剣**：3 段コンボ（4 / 4 / 8 ダメージ）。振り終わりの 200ms 前から押すと次の段へつながる。1・2 段目はほとんど押し出さず（コンボが届き続ける）、3 段目は大きく吹き飛ばす。振っている間の移動は 20%
- **回避**：320ms で素早く移動、最初の 260ms は無敵。剣を振り終わった後の硬直は回避で取り消せる。振っている途中に押した回避は 200ms 覚えておき、刃が通り過ぎた瞬間に出る。**開始から 150ms 以内に攻撃が当たるとジャスト回避**：1.5 秒間、敵と敵の弾が 20% の速さになる（主人公は通常の速さ）。避けた攻撃はその後も当たらない
- **ガード**：押している間、正面（左右 90°）からの攻撃を防ぐ（ダメージなし、少し押される）。歩きは 50%。**構えてから 150ms 以内に受けるとジャストガード**：近接の敵は 1.2 秒ひるみ、弾は跳ね返って敵に当たる
- **弓**：押して 400ms で引き絞り、離すと発射（それより早く離すと撃たない）。狙いはスティックの向き。**空中で構えると世界が 30% の速さ**になり、スタミナ 20/秒（実時間）を使う。矢の数の制限は P6
- **被弾**：ハートが減り、後ろに押され、800ms 無敵（点滅）
- **敵**：「澱の獣」（体力 12、近づいて 500ms 光ってから飛びかかる）、「澱の射手」（体力 8、距離 64〜112px を保ち、600ms 光ってから弾を撃つ。間隔 1.8 秒）。予備動作は赤く点滅して読める。水と崖の下には行かない
- **死亡と復活**：体力 0（戦闘・落下・溺れ）で「力尽きた…」と表示し、2 秒後に復活。敵は最初の状態に戻る（P3.5 から：最後に触れた記録石で復活）
- **操作**：タッチは右側に 攻撃（大）・ジャンプ・回避・弓・ガード・ダッシュ。キーボードは J 攻撃 / L 回避 / I ガード / U 弓 / Space ジャンプ / Shift ダッシュ（P2 まで J はダッシュだった）

### 5.6.2 実装メモ（P6 アイテムと装備）

- **データ**：`data/items.json` に、アイテム 26 種、レシピ、鍛冶の費用、敵の落とし物、最初の持ち物をまとめた。`npm run check:data`（CI でも実行）と単体テストで形式を検証する：ID の重複・形式、種類ごとの必須項目と数値の範囲、レシピ・鍛冶・落とし物・島の宝箱と落ちている物から、存在しないアイテムを参照していないか
- **お金**：「宝物」をやめて **星貨** と装備品にした（実機での感想を反映）。宝箱の中身は、ハートの器・星貨・装備のどれか。古いセーブは形式 v2 への移行関数で、宝物 1 個を 50 星貨に変換する
- **武器**：剣・槍・大剣・炎の剣（5 種）。威力・間合い・振りの速さ（遅い武器は振り全体が長い）・耐久度を持つ。敵に当たるたびに耐久が 1 減り、0 で壊れて次の武器に持ち替える。何もなければ素手（威力 1/4）。灯火の剣は、振った所の草木に火をつける
- **弓と矢**：弓がないと撃てない。1 本撃つごとに矢が 1 本減り、弓の耐久も 1 減る
- **防具**：頭・胴・足の 3 部位。防御の半分（切り捨て）だけ、受けるダメージが減る（最低 1）。特性：雷よけ（感電と雷が効かない）、岩登り（雨でも滑らない）
- **持てる量**：武器 6 本、弓 3 張、同じ物は 99 個まで。宝箱の中身を持てないときは、宝箱は閉じたまま
- **拾う**：島の 20 か所に素材・矢・武器が落ちている。上を歩くと拾い、ゲーム内 1 日で元に戻る（拾った時刻を保存）。倒した敵は、肉・牙・澱の結晶・矢を落とす
- **食べる**：素材も料理も、袋から食べて回復する。効果は、がんばり回復・攻撃力アップ（1.25 倍）・防御力アップ・炎に強くなる
- **料理**：たき火・かがり火の近くで「料理する」。素材を 1〜3 個入れる。レシピに合えばその料理になり、そのレシピを覚える（発見制。覚えたレシピだけ、入れる前に料理名が見える）。合わなければ「ごった煮」（回復は材料の 1.5 倍）、食べられない物だけなら「あやしい料理」
- **鍛冶**：丘の記録石の横に金床を置いた。星貨と素材で武器を +3 まで強化でき、1 段ごとに威力が 20% 上がり、耐久も満タンに戻る。修理は、減った耐久 1 につき 1 星貨
- **操作**：左上の「持ち物」、キーボードは E か Tab。開いている間はゲームが止まる。使える物の近くでは、画面下に「料理する」「鍛冶」ボタンが出る
- **まだ無いもの**：お店（P9 の住人と一緒に）、武器の種類ごとの動き（槍の突き、大剣の溜め）、アイテムの絵の作り込み（P11）

### 5.7 探索と謎解き
- **試練の洞（ためしのうろ）**：各地に点在する小さな謎解き施設（目標 30〜60 か所）
- **測量石**：高い所で使うと周辺の地図が描かれる
- **星環の能力**：蔓結び（足場・橋）、念動（軽い物体を動かす）、灯火（光の球）、共鳴（遠くの仕掛けを起動）
- **複数の解法**：仕掛けは「重さ・炎・電気・光・風」のどれでも動かせるように、入力の種類だけを判定する作りにする
- **ダンジョン**：大型施設が 4 つ（核の居場所）

### 5.7.1 実装メモ（P7 謎解きと能力）

- **場所**：`src/game/puzzles/abilities.js`（4 能力・箱・穴）、`switches.js`（仕掛けの部品）
- **仕掛けは入力の種類だけを見る**（5.7 の原則）。部品は 4 つ：
  - 重さの板：プレイヤー・敵・鉄の箱が乗っている間だけ
  - 光の目：光の玉・燃えている所・灯った燭台・かがり火が 40px 以内にある
  - 燭台：火矢・灯火の剣・隣の火で灯り、そのまま灯り続ける
  - 共鳴石：共鳴の波か電気が届くと 10 秒間
- **扉の開け方**：部品には「扉（link）」と「組（group）」がある。どれか 1 組の部品が同時に全部入れば扉が開き、セーブされる（P4 の扉と同じ）
- **星環の 4 能力**（右の「能力」ボタン・キーボードは Q、切り替えは ⇄ か R・持ち物の「能力」）
  - 灯火：20 秒浮かぶ光の玉。暗い部屋を照らし、光の目を動かす
  - 念動：前方 5 マス以内の鉄の箱を、ぶつかるまで滑らせる
  - 蔓結び：前方 3 マス以内の水や穴に、蔓の足場を作る。6 つまで、60 秒で枯れる。燃える（火で焼けると元の水・穴に戻る）
  - 共鳴：半径 7 マスの共鳴石を響かせる。壁ごしでも届く
- **箱**：鉄の箱は剣で叩くと 1 マス動く。鉄なので電気も通す
- **穴**：歩いて落ちると、落ちる前の場所に戻されて半ハート減る。ジャンプ中・滑空中は落ちない。敵は穴に近づかない
- **能力の入手**：試練の入口（光る石柱）に入るとその試練の能力が手に入る（灯り＝灯火、重さ＝念動、奈落＝蔓結び）。共鳴は灯台塔の頂上の祭壇に触れると手に入る
- **試練 3 つ**（島の東の別エリア。光る石柱から入る）。どれも 2 通り以上で解けることを単体テストで確認：
  - 灯りの試練（真っ暗な部屋）：①灯火の玉を光の目に近づける ②かがり火越しに火矢を撃ち、光の目の横の燭台を灯す ③灯火の剣で燭台を灯す
  - 重さの試練（板 2 枚を同時に）：①念動で鉄の箱を板へ滑らせ、自分はもう 1 枚に乗る ②剣で箱を 1 マスずつ押す ③敵を板に乗せる
  - 奈落の試練（穴の向こうの仕掛けのどれか）：①かがり火越しの火矢で燭台を灯す ②蔓の橋で穴を渡って板に乗る ③共鳴で共鳴石を響かせる
- **ごほうび**：試練の宝箱から「星の欠片」。持ち物の「能力」で、1 つにつきハート +1（最大 10）か、がんばり +20（最大 200）
- **まだ無いもの**：試練の量産（P10）、測量石と地図、風の入力（P5 の風を仕掛けに使う）

### 5.9 最初の島の面白さの設計（P3.5）

最初の島は「小さくても、自分で見つけて、自分のやり方で解く」体験を凝縮した場所にする。

**設計の原則**

| 原則 | 具体的な作り方 |
|---|---|
| 遠くから見える探索目標 | 島の中央に高くそびえる**崩れた灯台塔**（どこからでも見える最終目標）。ほかに**巨大な一本木**、**海沿いの煙**（野営地＝敵の拠点）、**光る石柱**（試練の入口）を配置。画面の外にある目標も、高い場所に登ると見える |
| 隠し宝箱・秘密の洞窟 | 滝の裏の洞窟、崖の途中の岩棚、橋の下、木の葉の下に隠れた入口。「何か変だ」と気づく手がかり（色の違う岩、不自然な草の切れ目、鳥が集まる場所）を必ず置く |
| 地形と環境を使う謎解き | P3.5 では高さ・ジャンプ・登攀・滑空・水泳・弓で解ける謎。P4 以降、同じ島に炎や電気の謎を**追加**する（島を作り直さない） |
| 一つの問題に複数の攻略法 | 下の例のように、どの課題にも 2〜3 通りの解き方を用意する |
| 探索するほど新しい発見 | 目標に向かう途中で別のものが見える配置。歩いて 20〜30 秒ごとに何か（宝箱、景色、敵、手がかり）がある密度にする |

**複数の攻略法の例**

| 課題 | 攻略法 |
|---|---|
| 高台の宝箱を取る | ①崖を登る（スタミナの管理が必要）②灯台塔から滑空して降りる ③裏の秘密の洞窟を抜けて上に出る |
| 敵の野営地を突破する | ①正面から戦う ②崖の上から弓で狙い撃つ ③泳いで海側から回り込み、戦わずに宝箱だけ取る |
| 川の向こう岸へ渡る | ①泳ぐ（流れが速く、スタミナが必要）②上流の倒木を渡る ③高い所から滑空する |

**発見の流れ（プレイヤーの体験）**

```
浜辺で目覚める → 灯台塔が見える（行きたくなる）
   → 途中で煙が見える（寄り道したくなる）
   → 崖に阻まれる（登る？回り道する？）
   → 回り道の途中で滝の裏の洞窟を見つける（ご褒美）
   → 塔に登ると島全体が見渡せ、まだ行っていない場所に気づく
```

- 島の大きさの目安：およそ 128×128 タイル（歩いて端から端まで約 1 分半）
- 島の地図は先に紙の上（または簡単な図）で設計し、目標の見え方と導線を確認してから作る
- 完成の基準：初めて遊ぶ人が、説明なしで 30 分以上自分から探索を続けたくなること

### 5.9.1 実装メモ（P3.5 最初の島の試作）

- **地図**：112×72 タイル（島は西側 96 列、東端の 16 列は洞窟用の別エリア）。手作業でなく `tools/gen_island.py` で生成し、生成時に「傾斜がちょうど 1 段」「敵が木や岩の中にいない」などを検査する。目安の 128×128 より小さく始め、実機プレイの感想で広げる
- **遠くから見える目標**：中央の**灯台塔**（遺跡、4 段）は最初から発見済み。**野営地の煙**と**巨木**は、近づくか高台（2 段以上）に立つと「発見」になる。発見済みの目標が画面外にあるときは、画面の端に方向を示す矢印を出す
- **宝箱**（6 個）：北の岩棚（ハートの器）、塔の頂上（ハートの器）、洞窟、野営地、小島、森の隠れ場所。宝箱の前で攻撃ボタンを押すと開く（剣は振らない）。ハートの器は最大体力 +1 ハート（最大 6）で全回復
- **岩棚の宝箱の 3 つの攻略法**：①台地から 1 段の崖を登る ②塔の頂上から滑空して降りる ③秘密の洞窟を抜けて岩棚に出る
- **秘密の洞窟**：西の崖の切れ目（入口の穴）に北向きに歩いて入る。中は別エリアで、カメラは洞窟の中だけを映し、外は暗くする。北の出口は岩棚へ、南の光る床は入口へ戻る。3/4 視点では南側の高い壁がプレイヤーを隠すため、洞窟の南側は低い岩で閉じる
- **記録石**（3 個：浜辺・丘・野営地）：触れると光り、倒れたときにそこから再開する
- **保存（2.6 の簡易版）**：保存するのは進み具合（開けた宝箱、触れた記録石、現在の復活地点、発見した目標、宝物の数、最大体力）。位置は保存せず、「つづきから」は最後の記録石から始まる。宝箱・記録石のとき、1 分ごと、アプリ切り替え時（`visibilitychange` / `pagehide` / 一時停止）に保存。IndexedDB に A / B の 2 世代を 1 つのトランザクションで交互に書き、FNV-1a のチェックサムで検証、壊れていれば前の世代を読む（タイトル画面で知らせる）。新しい版のセーブは読み込まず、上書きもしない。失敗は原因ごとの文言で画面に表示（同じ原因は 1 回だけ）
- **タイトル画面**：「はじめから」「つづきから」。保存があるときに「はじめから」を選ぶと、次の保存で上書きされることを確認してから始める
- **まだ無いもの**：セーブの書き出し（文字列コピー）、手動セーブ、滝・橋の下・鳥の手がかり、地図。島の感想を聞いてから追加する

## 7. 開発上の重要ルール

### 7.1 基本ルール
1. **各段階で動作可能な状態を維持する**：`main` ブランチは常に遊べる状態にする。作業は段階ごとのブランチで行い、テストに通ってから統合する（7.6）
2. **既存の正常な機能を壊さない**：段階ごとに追加したテストは消さずに回帰テストとして残す。高さ検証マップと最初の島で毎回回帰確認する
3. **テストに合格してから次の段階へ進む**：完了条件（7.2）をすべて満たすまで次に進まない
4. **iPhone 実機で操作性を確認する**：段階ごとに実機チェックリスト（7.3）を実施し、`docs/device-tests/` に記録する
5. **仮素材と本番素材を簡単に差し替えられる構造にする**（7.5）

### 7.2 各段階の完了条件（共通）
- [ ] 単体テスト・E2E がすべて成功（CI が緑）
- [ ] 前の段階までのテストもすべて成功
- [ ] iPhone 実機チェックリストを満たす
- [ ] 性能が前の段階より大きく悪化していない（`docs/perf/` に記録）
- [ ] GitHub Pages に配布済みで、実機から遊べる

### 7.3 iPhone 実機チェックリスト（雛形）
- [ ] 起動して操作できる。読み込みが長すぎない
- [ ] 仮想スティックとボタンが思った通りに反応し、押し間違えない
- [ ] FPS：目標 60、最低でも 30 で安定
- [ ] ホームに戻って復帰しても正常に再開する
- [ ] 画面を回転しても表示が崩れない。ノッチやホームバーと UI が重ならない
- [ ] その段階で追加した機能の操作感（例：ジャンプの気持ちよさ）

### 7.4 先行機能の扱い
- その段階の範囲外の機能は作らない。必要になりそうでも、まずバックログ（9 章）に書く
- 実験的な機能は機能フラグで隠し、普段の動作に影響させない

### 7.5 素材の差し替え構造
- ゲームは素材を**論理名**で参照する（`player.walk.down` など）。ファイルの場所はマニフェスト（JSON）で対応づける
- 仮素材パックと本番素材パックは**同じ論理名・同じフレーム名・同じ足元の基準点**を持つ。マニフェストを切り替えるだけで差し替えられる
- フレームのサイズ、アニメーション速度、当たり判定の大きさは素材ではなく**データ側**で持つ。絵を変えても挙動が変わらない
- 仮素材は統一パレット（32〜48 色）を使い、スクリプトで生成する。本番素材は Aseprite の JSON アトラスで取り込む
- パレット違反や論理名の不足は、ツールで自動チェックする

### 7.6 ブランチ運用

- 基本ブランチは **`main`**（`master` は使わない）
- 作業は段階ごとのブランチで行う（例：`feature/p0-setup`、`feature/p1-movement`）
- 流れ：作業ブランチで開発 → push → プルリクエストを作成 → GitHub Actions のテストがすべて成功 → `main` に統合 → GitHub Pages に自動配布 → iPhone 実機テストを記録
- 実機テストで問題が見つかったら、次の段階に進む前に修正用のブランチで直す
- `main` に直接コミットしない（設計書の軽微な修正も、作業ブランチ経由で行う）

### 8.1 実装メモ（P8 オープンワールド基盤）

- **世界**：最初の島の下（南）に、地方の雛形を 2 つ並べた。風の草原（なだらかな丘・湖・風車跡）と、赤砂の荒野（砂丘・岩山・サボテン・オアシス。雨が降らない）。島の南の浜から砂の道（土手道）が続いている。地方は `tools/gen_world.py` で作り、`src/game/world/world.js` で 1 枚の地図につなぐ。屋外の幅は 96 マス、全体は 112 × 264 マス
- **何を読み込み・解放するか**：地形の数値（1 マス数バイト）は世界全体を持っても数十 KB なので、全部持つ。重いのは絵（スプライトと GPU のテクスチャ）なので、絵をチャンク単位で扱う
- **チャンク**：32 × 32 マス。カメラの周り（画面＋4 マス）を作り、画面から 1 チャンク以上離れたら捨てる（行き来でちらつかないよう、作る範囲と捨てる範囲に差をつける）。平らな地面はチャンクごとに 1 枚のテクスチャにまとめ、高い地形の行は今まで通りキャラクターと奥行き順に並べる
- **継ぎ目**：同じ行の高い地形は、東のチャンクほど後に描くよう順番に小さな差をつけた。1 枚の地図だった時と同じ順になる。「チャンクで描いた画面」と「全部を一度に描いた画面（`?chunks=all`）」がピクセル単位で同じことを E2E で確認している（チャンク 4 つの角、崖がある場所）
- **素材の束**：地方ごとに専用の絵の束（`region:plains` 花の草地、`region:desert` 赤い砂・サボテン）がある。その地方のチャンクを作るときに読み込み、最後のチャンクを捨てるときに解放する（参照の数で管理）。島の共通の束は常に読み込む
- **メモリが増え続けないこと**：島 → 草原 → 荒野 → 島 を 4〜5 周しても、生きているテクスチャ数（12）と表示物の数は変わらないことを E2E で確認（チャンクは何十回も作っては捨てている）
- **天候と地方**：天候は世界で 1 つ（風も同じ）。乾いた地方では雨が晴れに、雷雨がくもりになり、燃えている火も雨で消えない
- **セーブの差分保存**：地図ができた時から変わった物（燃えて切り株になった木・切ったいばら・割った水がめ・開いた扉・動かした箱・灯った燭台）だけを、元の場所のチャンクごとにまとめて保存する。読み込み時に新しく作った世界に当て直す。燃えた跡が残るようになった（P4 では残らなかった）
- **60 分の長時間プレイ測定**：計測パネルの「自動巡回 60分」（または `?map=world&tour=60&debug=1`）。主人公が 4 秒ごとに島・草原・荒野を巡り、30 秒ごとに FPS・テクスチャ数・表示物・チャンク数・JS メモリを記録する。終わるとレポートが出て、「増え続けていない」かを判定する
- **まだ無いもの**：地方の作り込み（P10）、ファストトラベル、地方ごとの天候の起きやすさの違い（今は「雨が降るか」だけ）

### 8.2 実装メモ（P9 住人）

- **村**：風の草原の北に「風見の村」。家 4 軒（3 × 2 マスの通れない建物）と、住人 5 人（村長・料理番・見張り・雑貨屋・子ども）。住人は家のまわりを歩き、主人公が近づくと止まってこちらを向く。絵は草原の束（`region:plains`）に入れ、草原を読み込んでいる間だけ描く
- **話しかける**：宝箱と同じく、住人の前で住人の方を向いて「攻撃」。近くにいると画面下に「話す（名前）」が出る（押しても話せる）。会話中は世界が止まる。文字送りは画面をタップ、または J / Enter / Space
- **会話はデータ**：`data/dialogue.json`。会話ごとに「始まり」の候補を上から調べ、条件（フラグ・クエストの状態・持ち物・お金）が全部合う最初のものから始める（最後の候補は条件なし）。各場面は台詞・選択肢・次の場面と、効果（フラグを立てる・クエストを始める / 報告する・物やお金を渡す・お店を開く）を持つ
- **クエスト**：`data/quests.json`。状態は「未受注 → 進行中 → 報告できる（目標を満たした）→ 達成」。「報告できる」は持ち物や訪れた地点から毎回求めるので、ずれない。3 つ：村長の「なくしたお守り」（荒野のどこかに落ちている）、料理番の「獣肉 3 つ」、見張りの「風車跡を見てきて」。持ち物の「クエスト」で一覧を見られる
- **お店**：`data/shops.json`。雑貨屋で星貨を払って買う。売るときは値段の半分。大事な物は売れない。装備中の最後の 1 つも売れない
- **データの検査**：`npm run check:data` が、会話の場面・クエスト・お店・品物・地点の参照がすべて存在するか、どの場面にもたどり着けるか、どのクエストにも始める会話と報告する会話があるかを調べる（CI でも実行）
- **保存**：フラグとクエストの状態を進み具合と一緒に保存する
- **テスト**：会話・フラグ遷移（初対面 → 再訪 → 受注 → 報告できる → 達成）を単体テストと E2E で確認
- **まだ無いもの**：住人の一日の予定（朝晩で居場所が変わる）、ほかの地方の村（P10）。家の中は P10.1 で追加

### 8.3 実装メモ（P10.1 家の中）

- **どこにあるか**：各地方の東側、屋外のカメラには映らない 16 列の帯（`tools/gen_world.py` の `room()`）。島の洞窟・試練の部屋と同じ仕組みで、部屋ごとにカメラの範囲（area）を持つ。部屋の外は何もない暗闇（通れない）
- **出入り**：家の扉の前（扉の 1 マス南）で上に歩くと中へ。玄関マットの上で下に歩くと外へ（どちらもワープ）。部屋に入ると名前が出る
- **壁**：奥の壁は 2 段高く、漆喰の面が見える。左右の壁は平らな通れない壁（高くすると下の角に壁の断面が見えるため）。手前は低い壁（3/4 の見下ろしでは、高い壁が主人公を隠すため。島の洞窟と同じ考え方）。家の壁は登れない
- **4 軒**：雑貨屋（店主はカウンターの向こうから動かず、カウンター越しに話せる）、料理番の家（かまどで料理できる）、長老の家（お守りを届けると棚に飾られる）、風見の宿（ベッド 4 つ）
- **眠る**：ベッドの前で「攻撃」か「眠る」ボタン。朝 6 時か夕方 18 時まで眠れる（ちょうどその時刻になる）。ハートが全回復し、保存される。眠っている間の世界は、全地方をその時刻で凍らせ、起きて近づいた所から今まで通りの早送り（4.4）で追いつく。同じ状況なら何度やっても同じ結果
- **明るさ**：人の住む部屋はいつでも暖かい明かり（夜でも暗くならない）。かまどは光る
- **まだ無いもの**：住人が家に帰る一日の予定、ほかの地方の家

### 8.4 実装メモ（P10.2 四季）

- **暦**：1 季節＝ゲーム内 7 日（実時間で 168 分）。春 → 夏 → 秋 → 冬 → 春。新しい世界は春の 1 日目から。季節は世界の時刻だけで決まる関数（`seasonAt`）なので、保存・早送り・眠りとそのまま噛み合う。画面の時計に「秋 3日目 10:00 晴れ」のように出る
- **天候**：季節ごとに起きやすさが違う（春は雨が多め、夏は雷雨が多め、秋は晴れとくもり、冬は雪）。冬は雨も雷雨も降らず、代わりに雪。雪も雨と同じく火を消し、燃え移らせない。崖は滑らない。荒野（乾いた地方）には雪も降らない。天候が変わる 3 時間の区切りは、その区切りの最初の季節で決める
- **見た目**：春は木に花、秋は紅葉と枯れ色の草、冬は雪の地面・雪をかぶった木・降る雪。夏は元の絵。季節の絵は季節ごとの束（`season:spring` など）で、その季節の間だけ読み込む。季節が変わると、新しい束を読み込み終えてから（それまで前の季節の絵のまま）全部のチャンクを一度に作り直し、前の束を解放する
- **採れる物・出る敵**：拾える物と敵の出現地点に「出る季節」を付けられる（`seasons`。無ければ一年中）。春は草原に疾風草、夏は赤い実、秋は森きのこ（草原と島の西の森）、冬は火照りの実。秋は草原に獣が 3 匹増え、冬は 1 匹が巣にこもる。季節が変わると、物を置き直し、敵を出し直す（「冬になった」と出る）。セーブを読み込んだ時も、その季節の敵になる
- **確認用**：`?season=winter`（その季節の 1 日目、同じ時刻）、`?weather=snow`
- **まだ無いもの**：寒さ・暑さ（防寒具）、凍る湖、季節ごとの住人の台詞

### 9.1 実装メモ（P11.1 PWA と起動時間）

- **ホーム画面に追加**：`public/manifest.webmanifest`（全画面・横向き・アイコン）。アイコンは `tools/gen_icons.mjs` が星環の紋章のドット絵から PNG を作る（画像ツール不要）。iPhone は Safari の「共有 → ホーム画面に追加」
- **電波がなくても遊べる**：ビルド時に `vite.config.js` が `sw.js`（Service Worker）を書き出し、その版のファイル一式（HTML・スクリプト・CSS・アイコン）を最初の起動で保存する。2 回目からはネットなしで起動して遊べる。保存先はその版の名前つきで、新しい版が来ると古い版のファイルは消す。ページ（HTML）だけはネットを先に見るので、新しい版はすぐ届く（途中で入れ替わった時は「次に開いたときから新しくなります」と出る）
- **気をつけた点**：サーバーは「Vary: Origin」を付けて返し、スクリプトは Origin 付きで読まれるため、厳密に照合すると保存したファイルが見つからない。アドレスだけで照合する。テストの自動操作中は登録しない（古いビルドが残ってテストを惑わせないように。`?sw=1` で有効）
- **起動時間**：ページ・スクリプト・ゲームの準備完了までの時間と通信量を測り、計測レポート（「計測 30秒」）に「起動にかかった時間」として載せる。2 回目以降は通信 0 KB（保存済み）になる
- **配信サイズ**（このときの計測）：スクリプト合計 約 237 KB（圧縮後）、うち本体 159 KB（地図データが大半）。軽くするのは P11.4

### 9.2 実装メモ（P11.2 音）

- **音声ファイルは使わない**：効果音も BGM も Web Audio で合成する（`src/audio/audioEngine.js`）。ダウンロードが増えず、電波がなくても鳴る
- **iPhone の決まり**：ページは触られるまで音を出せないので、最初のタップ／キーで音を始める。一時停止中と、アプリを裏に回したときは止める（再開のタップで戻る）
- **効果音**：ゲームは音を鳴らさない。画面側がゲームの出来事（剣を振る・当たる・ジャスト回避・弾く・宝箱・拾う・記録石・扉が開く・クエスト・ボス・雷・眠る・季節が変わる など）を見て、対応する音を鳴らす（`src/audio/cues.js` の対応表）。同じ音は 40 ms 以内に重ねない
- **BGM**：8 曲（タイトル・草原・荒野・雪山・夜・洞窟・村・ボス戦）。どれも「テンポ・調・旋法・和音進行」のデータで、ベース・分散和音・和音から選ぶ旋律を、先読みしながら鳴らす（毎回同じ曲になる）。場所で切り替わり、切り替えはなめらかにつなぐ：タイトル → ボス戦中 → 家の中（村）→ 洞窟・試練・坑道 → 夜（20〜5 時）→ 荒野・雪山 → それ以外は草原
- **音量**：一時停止画面の「BGM」「効果音」ボタンで 0（オフ）→ 25 → 50 → 75 → 100% と切り替わり、端末に保存される（初期値：BGM 50%、効果音 80%）
- **テスト**：対応表・曲の選び方・曲が毎回同じであること・すべての効果音が実際に音を作ること（Web Audio の代わりを使う単体テスト）、最初のキーで音が始まる・場所で曲が変わる・一時停止で止まる・音量が保存される（E2E）
- **まだ無いもの**：足音や環境音（風・雨・水）、曲ごとの作り込み（P11.5 以降に、本番の作曲を入れるなら差し替え）

### 9.3 実装メモ（P11.3 遊びやすさと難易度）

- **設定画面**：一時停止画面の「設定」から（`src/ui/settingsMenu.js`）。選ぶとすぐ反映され、端末に保存される（セーブとは別。同じ端末なら、どのセーブでも同じ設定）
- **難易度**：やさしい（受けるダメージが半分）／ふつう／むずかしい（1.5 倍）。四分の一ハート単位で四捨五入し、最低でも 1。防具で減らす前にかける。ジャスト回避・ジャストガードの受付時間は変えない（腕前の手ごたえは同じ）
- **文字の大きさ**：大きいにすると、会話・お知らせ・持ち物・お店・設定・ボスの体力バー・「話す」などのボタンが 1.22 倍。画面上部の時計と所持金は重ならないよう元の大きさのまま
- **ボタンの大きさ**：小（0.85 倍）／中／大（1.15 倍）。ボタンの大きさだけでなく間隔もまとめて変えるので、重ならない（E2E で全組み合わせを確認）
- **持ち方**：左手でボタンにすると、ボタンの塊が左下へ移り、スティックは画面の右半分で出る
- **音量**：BGM・効果音（一時停止画面のボタンと同じ値）
- **まだ無いもの**：振動（iPhone の Safari は振動に対応していない）、ボタン配置の自由な調整、色覚への配慮（色だけで区別している所の洗い出し）

### 9.4 実装メモ（P11.4 最適化）

- **計測のしかた**：起動の各段階に目印（`performance.mark`：boot → renderer → art → world → view → save）を付け、自動ツアーの報告（`loadTiming.steps`）に段階ごとの時間が出る。比較は、回線を 4G 相当（遅延 150ms・9Mbps）、CPU を 4 倍遅くしたブラウザで、キャッシュなしの初回起動を 5 回測った中央値
- **PixiJS を別ファイルに**：描画ライブラリを本体から切り離し、HTML から先読みさせる。本体と並んで届くので待ち時間が減り、ゲームを更新してもライブラリ部分はキャッシュがそのまま使える
- **古いセーブ用の表を後から読む**：P10 以前のセーブを直すための物の一覧（約 31KB）は、古いセーブがあるときだけ読み込む
- **地図データ**：JSON の空白を省いた（元ファイル 146KB → 130KB。配信物は元々圧縮済みで変わらない）。連続を数字で書く方式（RLE）は、元の大きさは 1/4 になるが、圧縮後はもともと 11KB 程度しかなく得が小さいので見送った
- **結果**：本体 640KB → 363KB（圧縮後 90KB）＋ PixiJS 512KB（圧縮後 146KB、先読み）。起動完了まで 1291ms → 1119ms、うち描画の準備 391ms → 213ms
- **メモリと描画**：P8 の周回テスト（世界を何周しても増えない）と、遠くの地方の絵を手放すテストがそのまま通ることを確認。描画の数は P8 のチャンク方式のまま

- **住人の出現**（`src/game/npc/npcs.js`）：住人に `if`（会話の始まりと同じ条件。全部そろっている間だけいる）と `ghost`（半透明）。毎ステップ条件を調べ、そろえば足し、外れれば消す（話している相手は会話が終わるまで残す）。並びは地図の定義の順。半透明は核を 1 つ浄化するごとに少し濃くなる（0.45 → 0.85）。絵は、その住人の絵が読み込まれていれば描く（村の仮の見た目は草原の束、姫の仮の見た目と本番の絵は共通の束）
- **新しい住人**（`tools/gen_world.py`・`gen_island.py` の最後に置くので、既存の物は動かない）：風見の村に村の女性（料理番の家の東）・鍛冶職人（見張りの西）・クリア後の姫（宿の前）、草原の東の峠の手前に旅人、記録石 6 つ（浜・草原・荒野・山・森・湖）の横に姫の写し身。絵は住人の絵の名前 `art`（無ければ ID）で決まる：`npc.<art>.*`。7 か所の姫（ID は `princess_beach` など）はみな `art: princess` で `npc.princess.*` を使う。`npc.woman.*`・`npc.smith.*` は本番の絵がある。`npc.traveller.*`・`npc.princess.*` は入りしだい差し替わる。それまでの仮の見た目は look 6〜9。記録石の横の姫は話せる距離を 18px にした（生き返る所は記録石の 1 マス下で、姫とは斜め約 23px。そこで攻撃しても会話にならず、剣を振る）。クリア後の姫は宿の前から動かない（`stay`。戸口に重ならない）
- **データ**：会話 5 つ（姫・終わり・旅人・村の女性・鍛冶職人）を足し、長老・料理人・見張り・雑貨屋・村の子には始まりの候補と場面を足した（既存の場面は 1 字も変えていない）。クエスト 5 つ、新しい武器「星鋼の剣」。武器の欄がいっぱいのときは、鍛冶職人が「手がいっぱいだ、どれか 1 本、折れるまで使ってから来な」（武器の欄が空くのは武器が壊れた時だけ）と言い、クエストは報告できるまま残る（素材も取られない。条件 `{ "slots": "weapon", "is": false }`）。ほかの道でクエストを終えようとしても、持てない武器の報酬は渡さずに「これ以上持てない」と出す
- **お知らせ**（`src/game/npc/storyNotices.js`）：4 つ目の核を浄化して「星環の呼び声」を報告していなければ「記録石のそばで、姫の写し身が待っている…」。v1.0 より前のセーブ（印のフラグ `story_v1` が無い）を読み込んだとき、姫に会っていなければ核の数に関係なく 1 回だけ「浜の記録石のあたりに、青い光が見える…」
- **テスト**：`tests/unit/story.test.js`。条件・出現・会話の流れに加え、**詰まりの総当たり**：9 つの物語の段階 × 核 0〜4 × 初対面のフラグの有無 × 長老の言い伝えの有無で、各クエストについて「未受注なら、そこにいる住人と話して受けられる」「報告できるなら報告できる」を、選択肢をすべてたどって調べる（住人の出現を含む）。闘技場の姫（`princess_end`）が置かれるまでは、源のクエストは会話 `ending` そのもので確かめる

**順番の考え方**：最初の島（P3.5）を「新しい仕組みを試す小さな実験場」として使い、環境・時間・アイテム・謎解きを島の上で完成させてから、チャンクで世界を広げる（P8）。広い世界を作る前に、遊びの手触りを固める。
