# 製品版アートのまとめ読み込み（release art packing）

ブランチ: `feature/release-art-packing`

## 何が困っていたか

製品版アート（`src/art-release/<グループ>/*.png`）は 1 コマ 1 枚の PNG です。
これまでは `import.meta.glob` で読んでいたため、ビルドすると 1 コマごとに小さな JS ファイルが 1 個できていました
（中身は PNG を文字に直したもの）。

- 主人公だけで 248 個、NPC が入ると約 770 個
- `?hero=release` で開くと、その数だけ通信が起きる（iPhone の 4G では遅い）
- オフライン用の Service Worker が、その全部を前もって保存しようとする

## どう直したか

ビルドのときに、グループごとに **1 枚の絵（シート PNG）＋ 1 個の表（JSON）** にまとめます。

- `tools/release-art-pack.mjs`：PNG を読んで 1 枚に並べ、PNG に書き戻す小さな道具（外部ライブラリなし、Node の zlib だけ）
  - 並べ方：背の高い順 → 名前順。コマとコマの間は 1 px あける
  - 幅は 64〜4096 の 2 のべき乗で、縦が横より長くならない一番せまい幅
  - 同じ PNG からは、いつも同じバイト列のシートと表ができる（キャッシュがむだに切れない）
- `vite.config.js` の `releaseArt` プラグイン：ビルド時に各グループを packing して、
  `dist/assets/release-<グループ>-<ハッシュ>.png` と `.json` を直接出力する。
  **src/ の中には何も作らない**（生成物を git に入れる必要も、.gitignore に足す必要もない）。
  ゲーム側には `virtual:release-art` というモジュールで、それぞれの URL を渡す。
- `src/view/assets/heroPrototype.js` の `releaseFrames(group)`：
  - ビルド版：シート PNG と表 JSON を 1 回ずつ読み、「名前 → シート上の位置」を返す
  - 開発サーバー（`vite`）：これまでどおり 1 枚ずつ読む（シートは作らない）。この 1 枚ずつ用のコードはビルドから消える
  - シートが読めなかったときは警告を出して空を返す（主人公はいつもの絵のまま、ゲームは止まらない）
- `src/view/assets/placeholderPack.js` の `withOverrides`：差し替え元が URL ならこれまでどおり読み、
  シート上の位置なら、そのコマだけを同じ大きさのキャンバスに 1 px ずつそのまま写して使う
  （拡大縮小なし、なめらか補間なし）。あとはこれまでと同じアトラス作り。

元の PNG（`src/art-release/**`）は一切さわっていません。いまも正本です。

### 見た目が変わらない理由

- 名前・大きさ・足元の基準（anchor）は元のファイルと同じ。名前の順番も同じ（名前順）なので、アトラスの並びも同じ
- シートは元の PNG と同じ形式（8 bit RGBA、色空間の情報なし）。ブラウザが色を変える要素がない
- 元の PNG に色空間の情報（gAMA / iCCP / cHRM）や 16 bit・インターレースが入っていたら、**ビルドを止めてファイル名を出す**
  （違う色で出るよりは止めるほうが安全）。今の 248 枚はすべて対象外の普通の PNG です
- 単体テストで、全 248 コマについて「シートから切り出したもの＝元の PNG」をピクセル単位で確認

## 数字（主人公 248 コマ、`npx vite build`）

| | 変更前 | 変更後 |
|---|---|---|
| dist/assets のファイル数 | 300 | 54 |
| dist 全体のファイル数 | 307 | 61 |
| dist/assets の合計サイズ | 1,294,831 バイト | 1,085,147 バイト |
| dist 全体の合計サイズ | 1,319,740 バイト | 1,100,581 バイト |
| 主人公の製品版アートの中身 | JS 248 個・計 282,516 バイト | PNG 93,276 バイト ＋ JSON 12,704 バイト（gzip 1.5 KB） |
| `?hero=release` で増える通信の数 | 248 回 | 2 回 |
| ふだんのプレイで最初に読む JS（index） | 410.6 KB（gzip 97.7 KB） | 377.5 KB（gzip 93.8 KB） |
| sw.js（前もって保存するファイルの一覧） | 13,301 バイト | 3,826 バイト |

- 残りの 48 個の小さな JS は、試作アート（`src/art-proto`、`?npc=proto` など）用で、今回は対象外
- ふだんのプレイの JS が 33 KB 小さくなったのは、248 個分の読み込み先リストがメインの JS から消えたため
- NPC の製品版（約 520 コマ）が入っても、ファイルは NPC 用に 2 個増えるだけです（`src/art-release/npc/` に置けば自動で packing される）
- 通信の数はビルド結果と仕組みからの計算です（実際のブラウザでの確認は E2E 担当が行います）

## テスト

- 追加：`tests/unit/releaseArtPack.test.js`（表の正しさ・重なりなし・全コマのピクセル一致・同じ入力から同じ出力・PNG の各フィルタの読み取り・色空間情報つき PNG の拒否・ゲーム側の切り出しと読み込み失敗時の動き）
- `npx vitest run`：38 ファイル 488 テストすべて合格
- `npm run lint` / `npm run typecheck` / `npm run check:data` / `npx vite build`：すべて成功
- 開発サーバー（`vite`）が起動し、`virtual:release-art` が `null` を返して 1 枚ずつ読みに戻ることを確認
- Playwright（E2E）は実行していません（担当者が実行）

## 気をつけること・確認したいこと

1. シートや表が読めないとき、これまでは「読めなかったコマだけ」いつもの絵になりましたが、今は「そのグループ全部」いつもの絵になります（ゲームは止まりません）。ふだんは起きないので問題ないと考えていますが、ご確認ください
2. NPC 用の読み込みを別のブランチで独自の `import.meta.glob` で作っている場合は、`releaseFrames('npc')` を使う形にそろえる必要があります
3. 開発サーバーでは今も 1 枚ずつ読みます（ビルド版だけがまとめ読み）。開発中の通信の多さは変わりません
4. 元の PNG に色空間の情報などが入ると、ビルドが止まります（エラーにファイル名が出ます）。その PNG を情報なしで保存し直せば通ります
